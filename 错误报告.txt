
错误报告
========

记录日期：2026-09-11

* 菜谱详情页分区右上角缺少关闭按钮
- 问题现象：进入菜谱详情后，概览、准备食材、烹饪过程和更多信息四个分区的右上角没有关闭入口，原本显示的说明文字也占用了截图标注的位置。
- 原因：关闭逻辑只放在料理大厅外层窗口标题栏，详情分区标题栏没有独立的关闭控件；各分区标题栏右侧仍渲染说明文字。
- 解决方案：在四个分区标题栏右上角统一增加可访问的关闭按钮，绑定已有的 `closeDetailView`；删除四个标题栏右侧说明文字，并通过相对定位和固定触控尺寸保持按钮在右上角可见。
- 验证结果：前端详情源代码测试通过，前端 52 项测试通过，前端构建通过；本地页面可正常进入主厨料理大厅。

* 多种输入食材生成的单道菜谱混入过多食材，且没有优先返回 B 站已有教程
- 问题现象：输入多种食材时，单道生成结果可能同时使用第三种及以上输入食材；菜谱排序也没有根据 B 站现成视频进行优先级调整。
- 原因：原有多菜谱提示只要求拆分食材，没有为每道菜锁定具体搭配，也缺少后端对单道菜谱实际使用输入食材数量的校验；生成完成后未根据视频搜索结果重新排序。
- 解决方案：为多食材请求按规则为每道菜分配一对核心食材，在提示词中明确每道菜只能使用一至两种输入食材；后端校验每道菜不得包含第三种输入食材且必须包含指定搭配；生成完成后按 `videoKeywords` 或菜名检索 B 站，有匹配视频的菜谱优先展示，检索失败则保留 AI 原始顺序。
- 验证结果：后端完整测试 431 项通过，菜谱服务专项测试通过；前端视频优先级测试和完整前端测试通过，前端构建通过。

* 单食材生成的第二、第三道菜谱内容重复
- 问题现象：输入“螃蟹”时第二、第三道菜谱重复；输入“鸡蛋”时三道菜谱都可能返回相同内容。
- 原因：三道菜谱由后端连续独立请求生成，后续请求原先只收到“风格不同”的通用提示，没有读取前面已生成的菜名、简介、食材和做法，因此模型可能重复输出同一道菜。
- 解决方案：后续菜谱提示词加入前序菜谱的去重上下文，明确禁止复用菜名、简介、食材清单和步骤；服务端按菜名或完整内容指纹检测重复，发现重复时自动换一种做法重试一次，仍重复则拦截并提示重新生成；前端增加“正在更换重复做法”的状态提示。
- 验证结果：新增重复检测、前序提示和自动重试测试；后端完整测试 434 项通过，前端完整测试 53 项通过，前端构建通过。

管理员端 AI 协议配置迁移版本冲突
- 问题现象：后端 Spring Boot 测试上下文无法启动，Flyway 报告新增协议迁移与项目已有迁移使用了相同版本号。
- 原因：项目已有手机号验证相关的 V4、V5 迁移，新增协议字段迁移不能复用历史版本号；Flyway 不允许重复版本号。
- 解决方案：将新增迁移调整为当前历史末尾的 `V30__add_ai_model_protocol.sql`，保留已有迁移版本不变。
- 验证结果：干净重建后 Flyway 成功校验 30 个迁移，定向后端测试继续通过。

管理员端 AI 协议配置同步器无法被 Spring 实例化
- 问题现象：应用上下文启动失败，提示 `DotEnvSynchronizer` 没有默认构造器。
- 原因：同步器同时提供了生产环境的字符串路径构造器和测试用的 `Path` 构造器，Spring 无法自动判断注入入口。
- 解决方案：为配置注入用的字符串构造器增加 `@Autowired`，保留 `Path` 构造器供单元测试使用。
- 验证结果：修复后干净构建成功，Spring 上下文可以正常启动。

管理员端 AI 配置集成测试污染本地 `.env`
- 问题现象：集成测试调用保存配置接口时，将测试用配置写入了项目根目录的真实 `.env`。
- 原因：测试环境沿用了生产默认的 `.env` 同步路径，测试数据没有和本地配置文件隔离。
- 解决方案：将测试环境的同步路径改为 `backend/target/test-ai-config.env`，并清理本次测试产生的五行 `AI_TEXT_RECIPE_*` 配置，未输出或保留任何密钥值。
- 验证结果：根目录 `.env` 不再包含本次测试新增的 AI 配置项，后续集成测试只写入 `target` 下的临时文件。

Anthropic 协议回归测试样例 JSON 转义错误
- 问题现象：Anthropic 客户端测试执行时提示响应不是有效 JSON。
- 原因：Java 文本块中的内层菜谱 JSON 引号未按响应字符串再次转义，测试样例本身生成了非法 JSON。
- 解决方案：改为先构造合法的菜谱 JSON，再用 `ObjectMapper` 序列化 Anthropic `content` 响应，避免手写嵌套转义。
- 验证结果：Anthropic 普通请求和流式请求定向测试均通过。

管理后台新增协议字段后的表单跨列样式错位
- 问题现象：新增“接口协议”后，原表单按第 3、4 项配置的跨列规则会让模型名称和 API Key 的布局不符合预期。
- 原因：表单项目数量增加后，接口地址和 API Key 的序号从第 3、4 项变为第 4、5 项，旧 CSS 选择器没有同步调整。
- 解决方案：将桌面端和移动端的跨列选择器更新为第 4、5 项，保证接口地址与 API Key 的布局一致。
- 验证结果：已重新检查模板与响应式样式，并重新执行前端构建。

管理员端 AI 配置保存请求漏传接口协议
- 问题现象：管理后台可以切换 OpenAI 兼容和 Anthropic 兼容，但保存配置时后端收不到最新协议。
- 原因：前端测试连接请求包含 `protocol`，保存配置请求对象却遗漏了该字段。
- 解决方案：保存配置时同步提交当前接口协议；清空地址后切换服务商或协议时自动恢复对应默认地址。
- 验证结果：前端 55 项测试通过，生产构建通过，变更检查通过。

管理员端 AI 配置同步失败
- 问题现象：点击保存配置时报 `AI 配置已保存，但 .env 同步失败`，后端堆栈根因是 `/app/config/.env.tmp` 的 `AccessDeniedException`。
- 原因：Docker 容器中的 Java 进程以 `app` 用户运行，挂载的 `.env` 文件可写，但 `/app/config` 父目录由 `root` 管理且不可写；原同步器先在同目录创建临时文件，无法完成创建。
- 解决方案：改为直接截断并写入已有 `.env` 文件，绕过 bind mount 父目录的临时文件创建限制；保留数据库事务回滚和权限错误提示。
- 验证结果：容器内确认 `.env` 文件可写但父目录不可写；同步器单元测试、后端全量测试和构建检查通过，测试临时文件已清理。

实际菜谱联调等待窗口超时
- 问题现象：输入“鸡蛋”进行实际生成时，第三道菜谱生成期间浏览器自动化等待超过单次执行时限并重置了测试会话。
- 原因：真实 AI 流式生成需要等待多道菜谱依次返回，单次浏览器自动化等待时限短于完整生成耗时；不是前端或后端接口报错。
- 解决方案：重新连接原有测试页面，不重复提交请求，继续读取最终页面状态。
- 验证结果：页面最终显示 `3 / 3 道已完成`，返回西红柿炒鸡蛋、豆腐蒸鸡蛋、青菜蛋花汤，浏览器和后端错误日志均为空。

* qwen3 菜谱生成速度明显变慢
- 问题现象：本机切换到 qwen3.8-max 后，菜谱生成速度明显低于之前使用 qwen-plus 的体验。
- 原因：qwen3 系列默认可能启用思考过程，而菜谱接口原本没有关闭思考，也没有限制单次输出长度；生成三道菜时会额外等待较长的推理和输出内容。
- 解决方案：保留管理员端选择的模型，不强制替换为 qwen-plus；针对 qwen3 模型请求增加 `enable_thinking=false`，并将单道菜谱最大输出限制为 2400 tokens，同时保留 SSE 流式返回。
- 验证结果：qwen3 请求参数定向测试通过；本机 Docker 联调输入“鸡蛋”约 50 秒完成，页面显示 `3 / 3 道已完成` 且三道菜谱内容不同。

* 管理员端 AI 配置未传递到图像识别
- 问题现象：管理员端保存 AI 配置后，食材识别台仍可能调度失败，视觉请求没有稳定使用管理员端保存的地址和协议。
- 原因：视觉客户端此前直接使用环境默认地址，没有把管理员端保存的 Base URL 补全为 `/chat/completions`；同时请求体和响应解析只覆盖 OpenAI 兼容格式，无法完整适配 Anthropic 兼容配置。
- 解决方案：让视觉配置复用已保存的 Qwen 文本配置地址、密钥和协议；OpenAI Base URL 自动补全路径，Anthropic 使用对应请求头、图片内容结构和响应解析，并保留 `qwen-vl-plus` 视觉模型。
- 验证结果：本机通过食材识别接口上传食物图片成功返回“牛肉、青椒、红椒、姜”，返回模型为 `qwen-vl-plus`；视觉配置和客户端定向测试通过。

Docker 后端重建网络依赖失败
- 问题现象：第一次重建时 Ubuntu 软件源连续返回 502；绕过后，Docker 内 Maven 下载 `spring-webmvc` 时又出现文件传输提前结束。
- 原因：镜像构建依赖外部 Ubuntu/Maven 软件源的瞬时网络稳定性，且原 Dockerfile 每次构建都需要安装 `curl`。
- 解决方案：健康检查改用 BusyBox 提供的轻量 `wget`，移除 Ubuntu `apt-get` 依赖；Docker Maven 构建增加持久缓存，减少后续重复下载。
- 验证结果：后端镜像最终构建成功并启动为 healthy，前端和 MySQL 均保持 healthy。

新增 AI 请求测试样例 JSON 转义错误
- 问题现象：新增 qwen3 速度测试和图像识别测试第一次执行时报 JSON 解析错误。
- 原因：模拟接口响应中嵌套 JSON 字符串少了一层 Java 引号转义，测试样例本身不是合法响应。
- 解决方案：修正测试数据的双层引号转义。
- 验证结果：相关定向测试 14 项全部通过，后端完整测试 442 项全部通过。

定向测试命令参数解析失败
- 问题现象：第一次执行包含多个测试类的 Maven 定向测试时，PowerShell 报参数列表解析错误，测试未启动。
- 原因：包含逗号的 `-Dtest` 参数未整体加引号，被 PowerShell 按表达式解析。
- 解决方案：将 Maven 参数整体加引号后重新执行。
- 验证结果：定向测试随后成功执行，相关 14 项全部通过。

源码检查命令中的 PowerShell 变量展开错误
- 问题现象：读取三个 Java 源文件时，嵌套 PowerShell 命令中的文件路径变量被提前展开，导致命令提示找不到路径；代码和项目运行未受影响。
- 原因：外层 PowerShell 在调用内层命令前先解释了 `$p` 变量，内层 `Get-Content` 实际没有收到文件路径。
- 解决方案：改用带引号的直接文件路径读取，随后成功读取并检查相关源文件。
- 验证结果：核心服务测试 35 项全部通过，未发现源码读取或编码问题。

* B 站生成前检索被接口风控拦截
- 问题现象：用原有项目 User-Agent 访问 B 站视频搜索接口时返回 412，无法取得可信视频标题；若直接放行会破坏“无来源不生成”的安全约束。
- 原因：B 站接口对非浏览器请求头触发安全风控，原客户端只有项目自定义 User-Agent，没有来源页和 Origin 信息。
- 解决方案：改用常见浏览器请求头，并补充 B 站页面 Referer 与 Origin；保留原有 HTTPS、响应结构校验和失败闭环。
- 验证结果：同一食材检索接口已返回真实视频候选，客户端、生成前核验和失败闭环测试均通过；后端完整测试 446 项全部通过。

Docker 容器内 B 站请求仍被出口风控拦截
- 问题现象：宿主机直接访问 B 站搜索接口可以返回真实结果，但通过本机 Docker 部署生成菜谱时，生成前核验提示“未找到与当前食材匹配的可核验 B 站菜谱视频”。
- 原因：Docker 容器使用的出口网络被 B 站返回 412 风控响应，即使补齐浏览器请求头也无法取得视频结果。
- 解决方案：保留“未取得 B 站可信来源就不生成”的严格策略，避免模型在外部检索失败时胡编菜肴；要恢复 Docker 中的真实生成，需要放行容器出口或配置可访问 B 站的合规代理/上游服务。
- 验证结果：容器内请求明确返回 B 站 code=-412，宿主机请求返回 code=0；SSE 正确发送错误事件并停止生成，没有放行无来源菜谱。

Docker 健康检查工具与运行时 libc 不兼容
- 问题现象：尝试将 BusyBox 的 wget 复制到 JRE 运行镜像后，容器内执行该工具报 GLIBC_2.38 不满足，健康检查工具与运行时环境不兼容。
- 原因：BusyBox 构建阶段的二进制依赖比运行阶段 Ubuntu Jammy 提供的 libc 版本更新。
- 解决方案：移除跨镜像复制的 BusyBox wget，改用运行镜像自带的 `/usr/bin/curl` 执行健康检查，避免额外安装软件源依赖。
- 验证结果：后端镜像重新构建成功，后端、前端和 MySQL 容器均为 healthy。

本轮动态菜谱数量改造首次编译失败
- 问题现象：将菜谱数量改为动态后，后端编译提示流式服务仍引用已删除的固定数量常量。
- 原因：批次总数和列表容量的两处旧引用没有同步替换为动态数量。
- 解决方案：改为使用本次请求计算出的 3 至 5 道菜谱数量，并保留非法数量回退为 3 道。
- 验证结果：菜谱定向测试和后端全量测试均重新通过。

动态菜谱提示词回归断言未同步
- 问题现象：定向测试中原有 B 站提示词断言失败，测试期待“不得用模型记忆补写菜谱”原句。
- 原因：新增无视频降级规则时将原句改写成了更具体的表述，功能逻辑正确但破坏了已有文案契约。
- 解决方案：恢复原有关键约束原句，同时补充“不得返回空数据”和“不得虚构菜式/视频”的降级规则。
- 验证结果：后端菜谱定向测试 31 项、前端定向测试 56 项、后端全量测试 450 项全部通过。

五道菜谱真实接口冒烟测试超过命令时间窗口
- 问题现象：输入 9 种食材进行真实 SSE 冒烟时，接口已返回 `total=5` 并生成前两道菜谱，但测试命令在 20 秒上限后结束。
- 原因：五道菜谱按顺序调用 AI 生成，单次冒烟命令的 20 秒时间上限不足以等待完整批次完成。
- 解决方案：确认批次数量、两种食材组合约束和无 B 站视频降级均已在前置事件中生效；完整批次联调应使用更长的等待窗口。
- 验证结果：Docker 后端、前端和 MySQL 均 healthy；SSE 已确认返回 5 道批次信号且未因 B 站无结果返回空数据。

五道菜谱批次中辅料别名被误判为第三种输入食材
- 问题现象：真实输入“番茄、鸡蛋、牛肉、土豆、青椒、洋葱、胡萝卜、香菇、豆腐”时，实际菜谱 ingredients 使用了番茄、鸡蛋和常见辅料“葱”，校验却提示包含第三种输入食材“洋葱”，导致 SSE 中断。
- 原因：输入食材与生成食材的模糊匹配允许任意子串匹配，单字辅料“葱”被错误匹配成“洋葱”。
- 解决方案：收紧短名称的模糊匹配规则，避免单字辅料通过包含关系匹配多字输入食材；同时为食材约束失败增加专用重试提示，明确要求遵守固定两种核心食材。
- 验证结果：新增“葱不应匹配洋葱”回归测试通过；重新构建 Docker 后，9 种食材真实 SSE 返回 5 道菜谱并收到 complete 事件。

新增食材约束回归断言初次放错测试位置
- 问题现象：为验证食材约束重试提示新增断言时，第一次插入到了重复菜谱测试，导致定向测试断言失败。
- 原因：按相同的 `streamRecipe` 调用次数定位代码时，误匹配了前一个测试方法。
- 解决方案：将断言移动到“第三种输入食材触发重试”的测试，并捕获第二次生成提示进行校验。
- 验证结果：菜谱定向测试 33 项、后端全量测试 452 项均通过。

* 动态菜谱数量取消上限后残留旧常量引用
- 问题现象：本轮取消菜谱数量固定上限后，后端编译仍提示 `RecipeRecommendationService` 引用了已删除的 `MAX_RECOMMENDATION_COUNT`。
- 原因：动态数量改造只替换了批次数量计算，食材配对列表的安全数量仍保留旧的最大值限制。
- 解决方案：配对列表改为使用本次请求计算出的批次数量，仅保留至少 3 道的兜底，不再引用固定上限常量。
- 验证结果：菜谱定向测试 38 项通过；后端全量测试 457 项通过；Docker 后端镜像重新构建并保持 healthy。

* 输入猪肉被误判为未覆盖输入食材
- 日期：2026-09-11
- 问题现象：流式生成输入“猪肉”时，模型偶尔返回“五花肉、猪里脊肉、排骨”等明确猪肉部位，系统却提示“AI 返回的菜谱组合未覆盖输入食材（缺少：猪肉）”，并中断生成。
- 原因：食材覆盖校验只按文本相等或连续包含判断，未将明确的猪肉部位归一化为“猪肉”；B站检索不是直接报错来源，截图消息来自批量食材覆盖校验。
- 解决方案：增加严格的猪肉部位别名归一化，并要求模型对肉类返回明确名称；保留未限定肉类名称的“肉丝/肉片”不直接视为猪肉。
- 验证结果：猪肉实际流式接口返回 `stream complete`；定向测试 40 项通过；后端全量测试 459 项通过；后端 Docker 健康检查通过。
