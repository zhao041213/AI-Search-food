# 用户偏好、最近搜索与菜谱管理设计

## 目标

在现有 AI 菜谱生成、搜索日志和个人菜谱基础上，补齐普通用户的个人使用闭环：

1. 保存饮食偏好，并在生成和重新生成菜谱时自动应用。
2. 点击食材输入框时展示最近 5 条成功搜索记录，可一键回填搜索条件。
3. 在“我的菜谱”中支持菜名搜索、餐次/目标筛选和删除。

本轮不实现拍照识别、成品图评价、烹饪步骤模式、真实短信或 APK 打包。

## 产品规则

### 饮食偏好

- 仅普通用户可以永久保存个人偏好。
- 偏好包含：口味、默认饮食目标、忌口食材、过敏食材。
- 口味使用单选值，例如清淡、家常、香辣、酸甜、不限。
- 忌口和过敏食材使用可编辑的文本列表，后端统一去除空项和重复项。
- 登录用户进入工作台时读取偏好；生成菜谱和菜谱再生成时自动提交偏好。
- 未登录用户仍可正常生成菜谱，但本轮不提供持久化偏好。
- AI 提示词必须明确排除过敏食材和忌口食材；无法满足时返回安全、克制的说明，不生成包含禁用食材的菜谱。
- 用户主动选择的当前目标优先于偏好中的默认饮食目标；未选择时才使用默认值。

### 最近搜索

- 复用现有 `search_logs`，不新建重复的搜索历史表。
- 只有 AI 成功生成菜谱后产生的搜索日志才会进入最近搜索。
- 普通用户点击食材输入框或输入框获得焦点时，加载并展示本人最近 5 条记录。
- 每条记录展示食材组合、餐次、目标和搜索时间。
- 点击记录只回填食材、餐次和目标，不自动调用 AI，避免误产生调用费用。
- 同一用户连续搜索完全相同的食材、餐次和目标时，界面只展示最新一条，最多显示 5 条不同记录。
- 接口只返回最近 5 条，不删除旧 `search_logs`。旧数据继续用于热门食材排行榜和统计。
- 游客和管理员不展示最近搜索下拉，也不能调用个人历史接口。

### 我的菜谱管理

- 菜名关键词搜索采用模糊匹配。
- 餐次和目标筛选支持“不限”以及已有业务枚举值。
- 搜索与筛选均由后端按当前用户 ID 执行，不能查询其他用户数据。
- 删除按钮需要二次确认。
- 删除菜谱时删除 `recipe_records`，已有外键级联删除对应食材和步骤。
- 删除菜谱不删除关联的 `search_logs`，保证热门统计和最近搜索仍完整。
- 删除当前打开的菜谱后，前端自动选择剩余列表第一条；列表为空时显示空状态。

## 数据设计

### 用户偏好表

新增 `user_diet_preferences`：

- `user_id BIGINT PRIMARY KEY`：关联 `users.id`，用户删除时级联删除。
- `taste VARCHAR(32)`：口味枚举。
- `default_goal VARCHAR(64)`：默认饮食目标。
- `avoid_ingredients TEXT`：JSON 字符串数组。
- `allergen_ingredients TEXT`：JSON 字符串数组。
- `created_at DATETIME`。
- `updated_at DATETIME`。

采用独立表而不是给 `users` 增加多个字段，避免认证实体承担饮食业务字段，也便于后续增加热量目标、疾病禁忌等配置。

### 搜索日志

沿用 `search_logs` 的 `user_id`、`query_text`、`meal_type`、`goal`、`input_type` 和 `created_at`。为最近搜索查询补充联合索引：

```sql
CREATE INDEX idx_search_logs_user_created
    ON search_logs(user_id, created_at);
```

不对历史记录做物理裁剪。

## 后端接口

### 饮食偏好

- `GET /api/users/me/diet-preferences`：返回当前普通用户偏好；未创建时返回默认空对象。
- `PUT /api/users/me/diet-preferences`：校验并覆盖保存当前普通用户偏好。

请求和响应结构：

```json
{
  "taste": "light",
  "defaultGoal": "balanced",
  "avoidIngredients": ["香菜"],
  "allergenIngredients": ["花生"]
}
```

菜谱生成请求增加可选 `dietPreference`。后端不信任前端身份字段，只使用请求中的偏好内容生成本次菜谱；登录用户前端默认从已保存偏好填充。后端提示词对列表做长度和内容限制，避免异常超长输入。

### 最近搜索

- `GET /api/search-history/recent`：返回当前普通用户最近 5 条去重后的成功搜索记录。

响应项包含：`id`、`ingredients`、`mealType`、`goal`、`searchMode`、`createdAt`。服务层按 `user_id` 和时间倒序查询有限候选集，再按“标准化食材 + 餐次 + 目标”去重并截取 5 条。

### 我的菜谱

扩展现有接口：

- `GET /api/recipes/saved?keyword=&mealType=&goal=&limit=50&offset=0`。
- `DELETE /api/recipes/saved/{id}`。

删除接口必须同时校验菜谱存在且属于当前用户。对于不存在或不属于当前用户的 ID，返回统一资源不存在响应，避免泄露归属信息。

## 前端交互

### 工作台

- 在现有搜索参数区域增加“饮食偏好”入口，点击后使用紧凑抽屉或弹层编辑，不挤压桌面端首屏工作台高度。
- 弹层包含口味单选、默认目标选择、忌口标签输入和过敏标签输入。
- 登录用户可保存；保存成功后更新当前生成参数。
- 食材输入框聚焦时显示最近搜索下拉，最多 5 条。
- 点击历史记录回填食材、餐次和目标，并关闭下拉。
- 生成和重新生成请求都携带当前偏好。

### 我的菜谱

- 列表顶部增加菜名搜索框、餐次筛选和目标筛选。
- 筛选条件变化时重新查询第一页。
- 每条菜谱增加删除图标按钮和中文提示；确认后调用删除接口。
- 保持现有左右详情布局与堆叠页签，不重构无关页面。

## 权限与错误处理

- 所有新增个人接口要求有效 `USER` JWT。
- 管理员不显示饮食偏好、最近搜索和我的菜谱入口。
- 偏好字段非法时返回参数错误并显示中文提示。
- 最近搜索加载失败不阻止用户手动输入和生成，仅关闭下拉并给出轻量提示。
- 菜谱删除失败时保留当前列表和详情状态。
- AI 调用失败不写入搜索日志，沿用现有行为。

## 测试范围

### 后端

- Flyway 在 H2 与 MySQL 兼容语法下创建偏好表和索引。
- 偏好查询默认值、保存覆盖、字段校验和用户隔离。
- 菜谱提示词包含口味、忌口和过敏约束，再生成同样携带偏好。
- 最近搜索只返回当前用户、按时间倒序、去重且最多 5 条。
- 游客和管理员访问个人接口被拒绝。
- 菜谱关键词/餐次/目标组合筛选正确。
- 删除仅作用于当前用户菜谱，子表级联删除，搜索日志保留。

### 前端

- 搜索历史下拉只对普通用户显示，点击记录正确回填但不自动生成。
- 偏好数据正确加载、保存并进入生成和再生成请求。
- 菜谱筛选参数正确传递，删除确认成功后更新列表。
- 现有上传图片识别、菜谱保存、热门排行和管理员后台不受影响。
- 运行工具测试、生产构建和桌面/移动端浏览器检查。

## 明确不做

- 不删除超过 5 条的 `search_logs`。
- 不为游客保存本地搜索历史或偏好。
- 不实现偏好健康诊断或医疗建议。
- 不重构现有认证、热门排行或菜谱生成主流程。
