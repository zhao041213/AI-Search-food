# 搜索记录与个人菜谱保存设计

## 目标

在保留现有 AI 菜谱生成、上传图片识别和中文界面的基础上，实现搜索记录自动留存、用户主动保存菜谱和个人历史菜谱查看。桌面端采用已确认的 A 方案：左侧文字导航栏，后续功能预留空白入口。

## 已确认的产品规则

1. AI 生成成功后自动保存一条搜索记录，用于后续热门食材统计。
2. AI 菜谱不会自动进入用户的“我的菜谱”，必须点击“保存到我的菜谱”。
3. 登录用户保存的菜谱只归属于当前用户，其他用户不能查询或打开。
4. 游客可以生成菜谱，游客搜索也会记录，但游客点击保存时需要先登录。
5. 游客通过浏览器本地匿名 ID 关联连续搜索；匿名记录不作为用户个人历史展示。
6. 上传图片识别继续保留，流程为“上传图片 -> 千问识别 -> 用户确认食材 -> 生成推荐”。
7. 拍照识别只保留入口和未实现状态，本轮不调用摄像头、不提交识别请求。
8. 左侧导航保留“智能工作台”和“我的菜谱”，其余入口只做禁用占位，不绑定业务。

## 方案选择

### 方案 A：生成时直接保存为个人菜谱

生成成功后立即写入菜谱表，保存按钮只切换前端状态。实现简单，但无法准确区分“生成过”和“用户真正想保存”，也会污染个人菜谱列表。

### 方案 B：搜索记录自动保存，菜谱点击后保存

生成成功后只写入 `search_logs`；用户点击保存时提交当前生成结果，后端以 JWT 中的用户 ID 写入菜谱及子表。本方案符合“搜索可统计、菜谱需主动保存”的产品规则，个人历史更干净，推荐采用此方案。

### 方案 C：前端本地保存，登录时再同步

先把菜谱放入浏览器本地存储，登录后再上传。离线体验较好，但需要处理本地数据失效、跨设备同步和重复保存，当前阶段复杂度过高。

## 系统设计

### 1. 生成与搜索记录流程

1. 前端创建或读取 `anonymousId`，存储在浏览器 `localStorage`。
2. 前端调用现有 `/api/ai/recipes/generate`，同时发送 `X-Anonymous-Id` 请求头。
3. 后端先调用当前配置的 AI 文本模型。
4. AI 返回成功后，后端写入 `search_logs`：食材、餐次、饮食目标、输入方式、识别出的食材、模型和用户/匿名标识。
5. 响应保留现有菜谱字段，并增加 `searchLogId`，供保存菜谱时建立关联。
6. AI 调用失败或返回非法 JSON 时不写入搜索记录。

AI 网络调用不放在数据库事务中；只有搜索记录写入使用短事务，避免长时间占用数据库连接。

### 2. 保存菜谱流程

1. 用户点击“保存到我的菜谱”。
2. 未登录用户收到登录提示，登录成功后回到工作台；本轮不自动保存游客草稿。
3. 已登录用户调用 `POST /api/recipes/saved`。
4. 后端从 JWT 的 `AuthPrincipal.id` 获取用户 ID，不信任请求体中的用户 ID。
5. 后端校验 `searchLogId` 所属关系：已绑定其他用户的搜索记录不能被保存；当前匿名 ID 对应的游客记录可由同一浏览器登录用户关联。
6. 在一个事务内写入 `recipe_records`、`recipe_ingredients` 和 `recipe_steps`。
7. 保存成功后返回 `recipeId`、保存时间和完整菜谱内容，前端按钮切换为“已保存”。

保存请求包含当前 AI 返回的完整菜谱字段；后端同时写入 `raw_response`，便于后续模型升级和问题追踪。

### 3. 我的菜谱

新增接口：

- `GET /api/recipes/saved?limit=20&offset=0`：查询当前用户保存的菜谱摘要，按保存时间倒序。
- `GET /api/recipes/saved/{id}`：查询当前用户保存的菜谱详情。
- `POST /api/recipes/saved`：保存当前生成结果。

历史列表包含菜名、搜索食材、餐次、饮食目标和保存时间。详情复用现有食材、步骤、功效和提示的堆叠展示，不重新调用 AI。

本轮不添加删除、取消保存、收藏夹分类和分享链接，避免扩大当前功能范围。

### 4. 前端布局

- 使用 A 方案固定左侧文字导航栏。
- “智能工作台”进入首页工作区。
- “我的菜谱”进入个人历史页面。
- 其余导航按钮保持禁用占位，不显示虚假的功能页面。
- 主工作区提供“文字输入”和“图片识别”两个输入方式。
- 图片识别区保留上传区域、识别结果、确认按钮和拍照识别占位。
- 生成结果顶部提供“保存到我的菜谱”按钮，并包含加载、成功、失败三种状态。
- 桌面端控制整体高度和间距，尽量在 100% 缩放下显示完整工作区；小屏幕使用纵向布局。

## 数据库调整

使用新的 Flyway 迁移补足搜索条件和菜谱可读字段：

```sql
ALTER TABLE search_logs
    ADD COLUMN meal_type VARCHAR(64),
    ADD COLUMN goal VARCHAR(128);

ALTER TABLE recipe_records
    ADD COLUMN summary TEXT,
    ADD COLUMN effects TEXT,
    ADD COLUMN tips TEXT;
```

数组字段以 JSON 字符串写入 `TEXT`，由 Jackson 统一序列化和反序列化；`raw_response` 保留完整生成结果。

## 错误处理与权限

- 未登录访问个人菜谱接口返回 `401`。
- 访问其他用户的菜谱详情返回 `403` 或统一的资源不存在响应，不泄露菜谱归属。
- 保存请求字段缺失或列表为空时返回参数错误。
- 保存过程中任一数据库写入失败，事务整体回滚。
- 游客匿名 ID 仅用于记录关联，不允许通过接口查询游客的全部历史。
- 拍照识别占位按钮不发起网络请求，并明确显示“功能暂未实现”。

## 测试范围

后端增加以下行为测试：

1. 生成成功会写入搜索记录，并返回 `searchLogId`。
2. AI 调用失败不会写入搜索记录。
3. 登录用户保存菜谱时使用 JWT 用户 ID。
4. 保存菜谱会在一个事务中写入主体、食材和步骤。
5. 游客保存被拒绝，其他用户不能查看当前用户菜谱。
6. 历史列表按时间倒序且只返回当前用户数据。
7. 图片识别生成请求仍能记录为图片输入方式。

验证命令：

```powershell
mvn "-Dmaven.repo.local=D:\\AI-Search-food\\.m2" test
npm run build
```

## 明确不在本轮范围内

真实拍照识别、热门食材图片排行榜、缺失食材与替代建议、饮食偏好、菜谱再生成、采购链接、真实视频搜索、成品评价、收藏删除和管理员数据看板将在后续独立功能中实现。
